# Veynrel 2.0.0

Veynrel 2.0 brings a clearer view of your knowledge: what needs attention, how your notes connect, and which semantic relationships are worth exploring. Building on the Health, native Recall and Connect workspace introduced in 1.9.0, this release adds visual maps, connection comparison and a consolidated interface across the product. You can start with local Health and spaced repetition before configuring any AI provider.

## Health at a glance

The Health dashboard now leads with **Vault Pulse**, a recommended next step and current data. Its four dimensions remain **Structure, Connections, Recall and Knowledge**, with visible states, counts and coverage rather than an opaque 0–100 health score.

Vault Pulse gives Health a consistent visual identity while keeping the underlying state readable. Its waveform is not a heart-rate measurement or a new quality metric. The dashboard brings together Findings, the last local check, Recall and Knowledge status so you can see what deserves attention without reading through setup instructions.

**Vault Topology** adds a map of the Markdown links you actually created. Explore the graph, search for notes and inspect their connections. Partial coverage remains visible; missing metadata is not treated as proof that a note has no links.

Findings remains the action inbox: inspect evidence and affected notes, dismiss or snooze an observation, and reopen it when needed. Supported checks resolve findings after a later analysis confirms that the underlying issue is gone. The local Health scan does not require an AI provider.

## Semantic exploration

Discover now groups search, related notes and potential duplicates with three visual exploration surfaces:

- **Semantic Neighborhood** centers on one note and its closest semantic neighbors, with a text list and supporting evidence alongside the graph.
- **Global Semantic Map** shows the eligible indexed knowledge space. Its default center is the vault's **semantic core**; distance from that center represents similarity to the core.
- **Selected-note focus** lets any mapped note become the center. Radius then represents similarity to that note, and you can reset to the semantic core.

Node size on the Global Map reflects semantic connectedness, not importance or note quality. The maps reuse existing embeddings; opening, focusing and refreshing them does not request new embeddings. Search and inspectors provide ways to explore the same evidence without relying solely on the visual graph.

The exact Global Semantic Map currently supports **up to 500 eligible mapped notes**. Indexed and mapped counts may differ when some indexed notes are not eligible for the map. Above the limit, Veynrel reports the limit instead of silently sampling the vault.

## Connection Opportunities

**Connection Opportunities** compares the sparse semantic top-5 graph with explicit Markdown links. It separates pairs into three categories:

- **Candidate:** a semantic top-5 relationship with no known Markdown link in either direction.
- **Aligned:** a semantic top-5 relationship that also has Markdown linkage.
- **Explicit-only:** a Markdown-linked pair outside the sparse semantic top-5 graph.

**Explicit-only does not mean semantically unrelated.** Your links may express chronology, contrast, prerequisites or other intentions that similarity ranking does not capture. Coverage notices identify relationships that could not be compared.

Candidate review includes mutual top-3, mutual top-5 and one-sided rank evidence, shared semantic neighbors, and Markdown direction where available. Search, layered filters and an optional Excalidraw presentation filter help you inspect the list. You can annotate candidates **Useful / Not useful / Unsure** during the current session; reviews are not persisted and are cleared when a new comparison replaces the evidence.

**Connection candidates are not proof that a Markdown link should exist. No automatic Markdown links are created.** You decide whether a relationship is useful in the context of your notes.

## Reliability

Semantic indexing now provides clearer progress and safe, actionable failure reasons. Provider rejection, authentication failures, rate limits, server failures and timeouts are distinguished without displaying raw provider responses or note content in diagnostics.

Hard chunk bounds address provider failures caused by oversized paragraphs and atomic Markdown blocks, including large code blocks. Long content is split within the existing configured bounds while preserving text safely. Rejected batches report bounded numeric diagnostics to help explain the failure.

Retryable HTTP failures, including rate limits and temporary server errors, use bounded retry behavior. Non-retryable failures are not repeatedly sent, and timeout handling does not start overlapping attempts. A normal full build publishes only after all required batches succeed, so a failed batch does not leave a partially published new index.

## Recall

Native Recall remains part of the complete workspace, continuing the **FSRS-6** scheduling introduced in 1.9.0. Use the built-in due queue, reveal an answer and rate it **Again / Hard / Good / Easy**, with keyboard shortcuts 1–4. No third-party spaced repetition plugin is required.

Cards use `Question::Answer` lines under the exact, case-sensitive `Flashcards` heading. Scheduling is local and survives restarts. AI card generation remains optional and explicit; it is separate from the native review flow. This release does not add decks, review-history analytics or an optimizer.

## Unified workspace

**Health | Findings | Discover | Recall | Connect | Tools | Settings**

The whole workspace now shares clearer typography, spacing and action hierarchy, with less repeated explanation. Maps, lists and inspectors follow consistent patterns, while secondary technical details use disclosures. Contextual Back labels identify the destination, and same-page updates preserve focus and scroll where appropriate.

Responsive layouts retain a wide desktop workspace and stack content in narrow panes. EN and RU copy has been reviewed across the product. Verification is strongest on Linux desktop, with a bounded Android emulator smoke; this is not a claim of universal mobile, theme or assistive-technology coverage. The README now presents the current product with representative screenshots and a local-first quick start.

## Upgrade & compatibility

The plugin name remains **Veynrel** and its ID remains **`ai-knowledge-hub`**. Use the normal Community Plugin update. For manual installation, replace `main.js`, `manifest.json` and `styles.css` in the existing `.obsidian/plugins/ai-knowledge-hub/` directory; do not create a second plugin folder.

Existing compatible settings and data are preserved. **No semantic rebuild is required merely because the plugin is now 2.0.0** when the existing index remains compatible. A first build or a rebuild after an incompatible embedding-space change is still explicit.

Upgrade verification used the actual published 1.9.0 assets and preserved settings, semantic index bytes, Health state, Recall schedules, Companion identity, hotkeys and user notes. Existing Health and semantic storage remain supported; Recall retains support for its tested v1, v2 and v3 formats, while unsupported future formats remain protected rather than silently reset. The minimum Obsidian version remains **1.8.7**.

## Privacy / explicit work

Local Health requires no provider, and Recall scheduling stays local. Remote semantic indexing sends the required note chunks to the selected embedding provider; semantic search sends the query. Deep Intelligence and Knowledge Health send the disclosed task input to the selected language model.

Connect sends its disclosed mirror to the configured Companion endpoint. Manual sync is confirmed explicitly; enabling Connect also permits disclosed incremental synchronization after subsequent semantic changes. External proposals require explicit approval in Obsidian before a vault write. Companion remains self-hosted, and opening the workspace does not itself trigger a scan, index build or synchronization.
